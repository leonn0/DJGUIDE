01 — Mental model

The request lifecycle

Django calls its pattern MTV — Model, Template, View — which is the same idea as MVC with different labels. Before touching any code, hold this shape in your head: an HTTP request enters, gets routed to exactly one view, the view talks to models and hands data to a template, and an HTTP response comes back out.

One request → one view → (models + template) → one response

The order that matters when you build: urls.py decides which view runs, the view is the controller that orchestrates everything, models define and fetch your data, and templates present it. Settings glue it all together. The rest of this document walks each layer with real code.

02 — Setup

Starting a project

Django distinguishes a project (the whole site + configuration) from an app (a self-contained feature module — blog, accounts, orders). One project holds many apps. Always work inside a virtual environment.

terminalbash
# 1. Isolated environment (per project, never global)
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# 2. Install and pin
pip install "Django==5.2.*" psycopg[binary] python-dotenv
pip freeze > requirements.txt

# 3. Create the project in the CURRENT dir (note the trailing ".")
#    Without the dot, Django nests an extra folder you don't want.
django-admin startproject config .

# 4. Create your first app
python manage.py startapp blog

# 5. Confirm it runs
python manage.py migrate
python manage.py runserver
Convention that pays off

Name the settings package config (or core) rather than repeating the project name. It keeps imports like config.settings stable even if the project gets renamed, and it reads clearly as "this is configuration, not a feature."

What the layout looks like

Here's a production-shaped tree. The key idea: apps live at the top level, settings live in config/, and cross-cutting folders (templates, static, tests) are explicit.

myproject/ ├── .venv/ # virtualenv (git-ignored) ├── .env # secrets, never committed ├── manage.py # CLI entry point ├── requirements.txt ├── config/ # the "project" — glue only │ ├── __init__.py │ ├── settings.py # or a settings/ package (see §03) │ ├── urls.py # root URLconf │ ├── asgi.py │ └── wsgi.py ├── blog/ # an "app" — one feature │ ├── __init__.py │ ├── admin.py │ ├── apps.py │ ├── models.py │ ├── views.py │ ├── urls.py # you create this │ ├── forms.py # you create this │ ├── migrations/ │ ├── templates/blog/ # namespaced by app │ └── tests/ └── templates/ # project-wide base templates
Why templates/blog/ and not templates/

Django's template loader searches all app template dirs and returns the first match. If two apps both have index.html, you get collisions. Namespacing each under a folder matching the app name (blog/index.html) makes every template path unambiguous. Same logic applies to static/blog/.

03 — Configuration

settings.py, done properly

The generated settings.py is fine for a first run but hard-codes secrets and a single environment. Real projects read config from the environment and keep DEBUG=False anywhere that isn't your laptop. Here's the shape you actually want.

# startup. Every UPPERCASE name here becomes globally readable via
# django.conf.settings. Secrets come from the environment, not the file.
# =========================================================================
from pathlib import Path
import os
from dotenv import load_dotenv

BASE_DIR = Path(__file__).resolve().parent.parent
load_dotenv(BASE_DIR / ".env")           # pulls KEY=value pairs into os.environ

    """Small helper so config reads clearly and fails loudly."""
    value = os.environ.get(key, default)

    return value

The three settings that cause real incidents

SECRET_KEY in the repo, DEBUG=True in production (it leaks your whole environment on any error page), and a wildcard ALLOWED_HOSTS = ["*"]. Get these three right and you've avoided the most common Django security mistakes.

Scaling up

When one file gets unwieldy, convert settings.py into a package: config/settings/base.py, dev.py, prod.py, each ending with from .base import *. Select with DJANGO_SETTINGS_MODULE=config.settings.prod.

04 — Data layer

Models

Definition

A model is a Python class that maps to one database table. Each class attribute is a column, each instance is a row. Django's ORM generates the SQL, so you rarely write it by hand.

Below is a realistic blog models file. Note what makes it production-grade: an abstract TimeStampedModel base, an explicit custom manager, database indexes and constraints, related_name on every relation, a get_absolute_url, and a Meta with sensible ordering.

blog/models.pypython
from django.conf import settings
from django.db import models
from django.urls import reverse
from django.utils import timezone
from django.utils.text import slugify


# --- Reusable abstract base ------------------------------------------------
# TEMPLATE: put common columns in an abstract model. abstract=True means
# Django creates NO table for it — the fields are copied into each child.
class TimeStampedModel(models.Model):
    created_at = models.DateTimeField(auto_now_add=True)   # set once, on insert
    updated_at = models.DateTimeField(auto_now=True)       # set on every save

    class Meta:
        abstract = True


# --- Custom manager: encapsulate common querysets --------------------------
# DEFINITION: a Manager is the entry point for DB queries (Model.objects).
# Subclass it to name your business-logic queries once, reuse everywhere.
class PublishedManager(models.Manager):
    def get_queryset(self):
        return super().get_queryset().filter(status=Post.Status.PUBLISHED)


class Category(TimeStampedModel):
    name = models.CharField(max_length=100, unique=True)
    slug = models.SlugField(max_length=100, unique=True)

    class Meta:
        verbose_name_plural = "categories"
        ordering = ["name"]

    def __str__(self):
        return self.name


class Post(TimeStampedModel):
    # TextChoices gives you an enum with DB value + human label + IDE autocomplete
    class Status(models.TextChoices):
        DRAFT = "DF", "Draft"
        PUBLISHED = "PB", "Published"

    title = models.CharField(max_length=250)
    slug = models.SlugField(max_length=250, unique_for_date="published_at")
    body = models.TextField()
    status = models.CharField(
        max_length=2, choices=Status.choices, default=Status.DRAFT,
    )
    published_at = models.DateTimeField(default=timezone.now)

    # RELATIONSHIPS ---------------------------------------------------------
    # FK  = many posts → one author. Always reference the user via settings.
    author = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,          # delete posts if the user is deleted
        related_name="posts",              # enables user.posts.all()
    )
    # FK to Category, but keep posts if the category is removed (SET_NULL)
    category = models.ForeignKey(
        Category, on_delete=models.SET_NULL,
        null=True, blank=True, related_name="posts",
    )
    # M2M = a post has many tags, a tag has many posts
    tags = models.ManyToManyField("Tag", blank=True, related_name="posts")

    # MANAGERS --------------------------------------------------------------
    objects = models.Manager()             # the default — keep it first
    published = PublishedManager()         # Post.published.all() → only PB

    class Meta:
        ordering = ["-published_at"]
        indexes = [
            models.Index(fields=["-published_at"]),
            models.Index(fields=["status", "published_at"]),
        ]
        constraints = [
            models.UniqueConstraint(
                fields=["slug", "published_at"],
                name="unique_slug_per_date",
            ),
        ]

    def __str__(self):
        return self.title

    def save(self, *args, **kwargs):
        if not self.slug:
            self.slug = slugify(self.title)
        super().save(*args, **kwargs)

    # CONVENTION: models own their canonical URL. Templates & redirects
    # call post.get_absolute_url() instead of hard-coding paths.
    def get_absolute_url(self):
        return reverse("blog:post_detail", kwargs={"slug": self.slug})


class Tag(TimeStampedModel):
    name = models.CharField(max_length=50, unique=True)
    slug = models.SlugField(max_length=50, unique=True)

    def __str__(self):
        return self.name

05 — Schema evolution

Migrations

You never write CREATE TABLE by hand. You change models.py, Django diffs it against the current schema, and generates a migration file — a versioned, reviewable Python description of the change. Migrations are committed to git and applied everywhere in order.

Model change → generate → review → apply. The file is the source of truth.

terminalbash
# Generate migration files from model changes (does NOT touch the DB)
python manage.py makemigrations blog

# See the SQL a migration will run, before running it
python manage.py sqlmigrate blog 0002

# Apply all unapplied migrations to the database
python manage.py migrate

# Inspect state: [X] = applied, [ ] = pending
python manage.py showmigrations

# Roll back to an earlier migration (0001) — reverses 0002+
python manage.py migrate blog 0001

# Data migration scaffold (for backfilling / transforming rows)
python manage.py makemigrations --empty blog --name backfill_slugs
Golden rules

Always makemigrations and migrate as two separate steps — never edit the DB by hand. Commit migration files. And review the generated migration before applying to production: makemigrations occasionally makes a destructive choice (like dropping and recreating a column) that you'll want to rewrite.

06 — Querying

The ORM in practice

The ORM turns Python method chains into SQL. QuerySets are lazy — no query runs until you iterate, slice, or call something like list(). This lets you build a query up in pieces and hit the database exactly once.

ORM patternspython
from blog.models import Post, Category

# CREATE ------------------------------------------------------------------
post = Post.objects.create(title="Hello", body="...", author=request.user)

# READ — filter / exclude / get -------------------------------------------
Post.published.all()                          # custom manager → only published
Post.objects.filter(status="PB")              # WHERE status = 'PB'
Post.objects.exclude(author=request.user)     # WHERE NOT ...
Post.objects.get(slug="hello")                # exactly one row (or raises)

# Field lookups use double-underscore syntax -----------------------------
Post.objects.filter(title__icontains="django")        # ILIKE '%django%'
Post.objects.filter(published_at__year=2026)          # date parts
Post.objects.filter(author__email="a@b.com")          # FK traversal (JOIN)
Post.objects.filter(category__slug__in=["news","hr"]) # IN + traversal

# Complex conditions with Q objects (OR / AND / NOT) ---------------------
from django.db.models import Q
Post.objects.filter(Q(status="PB") | Q(author=request.user))

# ORDER / SLICE / COUNT / EXISTS -----------------------------------------
Post.objects.order_by("-published_at")[:10]   # LIMIT 10, newest first
Post.objects.filter(status="PB").count()
Post.objects.filter(author=request.user).exists()

# AGGREGATE & ANNOTATE ---------------------------------------------------
from django.db.models import Count, Avg
Category.objects.annotate(n=Count("posts")).filter(n__gt=5)  # per-row count

# UPDATE / DELETE (in bulk, one SQL statement) ---------------------------
Post.objects.filter(status="DF").update(status="PB")
Post.objects.filter(published_at__year=2020).delete()

The N+1 problem — the one optimisation to internalise

Looping over posts and touching post.author inside the loop fires one extra query per post. On a page of 50 posts that's 51 queries. select_related (for FK/O2O) and prefetch_related (for M2M / reverse FK) collapse that into a small constant.

avoiding N+1python
# ❌ 1 query for posts + 1 query PER post for its author = N+1
for post in Post.objects.all():
    print(post.author.email)

# ✅ single JOIN pulls authors up front — 1 query total
for post in Post.objects.select_related("author", "category"):
    print(post.author.email)

# ✅ for many-to-many / reverse FK, prefetch_related does 2 queries
posts = Post.objects.prefetch_related("tags").select_related("author")
Debug your query count

Install django-debug-toolbar in dev — it shows the exact SQL and query count on every page. Watching that number is how you catch N+1 issues before they reach production.

07 — Routing

URLs & routing

Definition

A URLconf is an ordered list of URL patterns. Django walks it top to bottom on each request and dispatches to the first pattern that matches, passing any captured pieces to the view.

Best practice: the root URLconf in config/ only include()s per-app URLconfs. Each app owns its own urls.py with an app_name for namespacing. That's what makes reverse("blog:post_detail") work.

config/urls.pypython · root
from django.conf import settings
from django.conf.urls.static import static
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path("admin/", admin.site.urls),
    path("accounts/", include("accounts.urls")),   # delegate to the app
    path("", include("blog.urls")),                 # blog owns the root
]

# Serve user-uploaded media in DEBUG only (a real server handles this in prod)
if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
blog/urls.pypython · app
from django.urls import path
from . import views

# app_name enables namespaced reversing: reverse("blog:post_detail")
app_name = "blog"

urlpatterns = [
    # TEMPLATE: path(route, view, name)
    path("", views.PostListView.as_view(), name="index"),

    # PATH CONVERTERS capture typed segments: <type:name>
    # <slug:...> matches letters/numbers/hyphens, <int:...> digits, etc.
    path("post/<slug:slug>/", views.PostDetailView.as_view(), name="post_detail"),
    path("category/<slug:slug>/", views.PostListView.as_view(), name="by_category"),

    path("new/", views.PostCreateView.as_view(), name="post_create"),
    path("post/<slug:slug>/edit/", views.PostUpdateView.as_view(), name="post_edit"),
    path("post/<slug:slug>/delete/", views.PostDeleteView.as_view(), name="post_delete"),
]
ConverterMatchesExample route
<int:pk>Positive integerspost/<int:pk>/
<slug:slug>a-z, 0-9, hyphen, underscorepost/<slug:slug>/
<str:name>Any non-slash textuser/<str:name>/
<uuid:id>UUID stringsorder/<uuid:id>/
<path:p>Text including slashesfiles/<path:p>/
Never hard-code a URL

In templates use {% url 'blog:post_detail' slug=post.slug %}; in Python use reverse() or redirect("blog:index"); on models use get_absolute_url(). Then changing a route in urls.py updates every link automatically.

08 — Controllers

Views

Definition

A view is a callable that takes an HttpRequest and returns an HttpResponse. It's the orchestrator: read input, query models, run logic, pick a template or serialize, respond.

Django gives you two styles. Function-based views (FBV) are explicit and easy to read. Class-based views (CBV) package the common CRUD patterns so you write almost nothing. Use FBVs for one-off custom logic; use CBVs (especially the generic ones) for standard list/detail/create/update/delete.

Function-based view

blog/views.pypython · FBV
from django.contrib.auth.decorators import login_required
from django.shortcuts import get_object_or_404, redirect, render

from .forms import PostForm
from .models import Post


# TEMPLATE: def view(request, *captured_kwargs): ... return HttpResponse
def post_list(request):
    # select_related avoids N+1 on author (see §06)
    posts = Post.published.select_related("author", "category")
    # render(request, template_path, context_dict) → HttpResponse
    return render(request, "blog/post_list.html", {"posts": posts})


def post_detail(request, slug):
    # get_object_or_404 = get(), but raises a clean 404 instead of a 500
    post = get_object_or_404(
        Post.published.select_related("author"), slug=slug,
    )
    return render(request, "blog/post_detail.html", {"post": post})


# DECORATOR enforces auth: anonymous users are redirected to LOGIN_URL
@login_required
def post_create(request):
    if request.method == "POST":
        form = PostForm(request.POST)
        if form.is_valid():
            post = form.save(commit=False)   # build instance, don't hit DB yet
            post.author = request.user       # attach the logged-in user
            post.save()
            form.save_m2m()                  # needed after commit=False for M2M
            return redirect(post)            # uses get_absolute_url()
    else:
        form = PostForm()
    return render(request, "blog/post_form.html", {"form": form})

Class-based view — the same, shorter

The generic CBVs know the standard flow. A ListView fetches a queryset and renders it; a CreateView builds the form, validates on POST, saves, and redirects. You override only the pieces that differ.

blog/views.pypython · CBV
from django.contrib.auth.mixins import LoginRequiredMixin, UserPassesTestMixin
from django.urls import reverse_lazy
from django.views.generic import (
    ListView, DetailView, CreateView, UpdateView, DeleteView,
)
from .forms import PostForm
from .models import Post


class PostListView(ListView):
    model = Post
    template_name = "blog/post_list.html"
    context_object_name = "posts"          # {{ posts }} in the template
    paginate_by = 10                        # free pagination

    # Override to filter / optimise the queryset
    def get_queryset(self):
        qs = Post.published.select_related("author", "category")
        if slug := self.kwargs.get("slug"):
            qs = qs.filter(category__slug=slug)
        return qs


class PostDetailView(DetailView):
    model = Post
    template_name = "blog/post_detail.html"
    # DetailView looks up by pk or slug from the URL automatically

    def get_queryset(self):
        return Post.published.select_related("author")


# MIXINS compose behaviour: require login, then the create flow
class PostCreateView(LoginRequiredMixin, CreateView):
    model = Post
    form_class = PostForm
    template_name = "blog/post_form.html"

    # Hook: runs after validation, before save — inject the author
    def form_valid(self, form):
        form.instance.author = self.request.user
        return super().form_valid(form)


class PostUpdateView(LoginRequiredMixin, UserPassesTestMixin, UpdateView):
    model = Post
    form_class = PostForm
    template_name = "blog/post_form.html"

    # UserPassesTestMixin: only the author may edit
    def test_func(self):
        return self.get_object().author == self.request.user


class PostDeleteView(LoginRequiredMixin, UserPassesTestMixin, DeleteView):
    model = Post
    success_url = reverse_lazy("blog:index")

    def test_func(self):
        return self.get_object().author == self.request.user
Generic CBVDoesFBV equivalent
ListViewList a queryset (+ pagination)query → render list
DetailViewOne object by pk/slugget_object_or_404 → render
CreateViewShow form → validate → savethe POST/GET dance above
UpdateViewEdit an existing objectbound form on instance
DeleteViewConfirm → delete → redirectPOST → obj.delete()
Which to reach for

Start with a CBV when your view is "list these / show one / CRUD this model" — you'll write a fraction of the code. Drop to an FBV the moment the logic is genuinely custom (multi-step workflows, odd branching, several models at once). Mixing both in one project is normal and expected.

09 — Input

Forms & validation

Forms handle three jobs at once: render HTML inputs, validate incoming data, and clean it into Python types. A ModelForm derives all of that from a model, so you don't repeat field definitions. Validation is layered: field-level, then per-field clean_<field>, then a whole-form clean().

blog/forms.pypython
from django import forms
from django.utils import timezone
from .models import Post


class PostForm(forms.ModelForm):
    class Meta:
        model = Post
        # List fields explicitly — NEVER use "__all__" on user-facing forms,
        # or a user could POST fields like `author` or `status` you didn't intend.
        fields = ["title", "body", "category", "tags", "status", "published_at"]
        widgets = {
            "body": forms.Textarea(attrs={"rows": 12, "class": "input"}),
            "published_at": forms.DateTimeInput(
                attrs={"type": "datetime-local", "class": "input"},
            ),
        }
        help_texts = {"slug": "Leave blank to auto-generate from the title."}

    # FIELD-LEVEL validation: clean_<fieldname>() — must return the value
    def clean_title(self):
        title = self.cleaned_data["title"].strip()
        if len(title) < 5:
            raise forms.ValidationError("Title must be at least 5 characters.")
        return title

    # FORM-LEVEL validation: clean() — cross-field rules go here
    def clean(self):
        cleaned = super().clean()
        status = cleaned.get("status")
        published_at = cleaned.get("published_at")
        if status == Post.Status.PUBLISHED and published_at > timezone.now():
            self.add_error(
                "published_at",
                "A published post can't have a future date.",
            )
        return cleaned

form.is_valid() runs this pipeline; failures collect in form.errors

CSRF is not optional

Every POST form must include {% csrf_token %} inside the <form> tag. Django rejects POST requests without a valid token. This is on by default and protects against cross-site request forgery — don't disable it to "make the error go away."

10 — Presentation

Templates

Django templates render HTML from context data. The pattern that scales is inheritance: a single base.html defines the page shell with named {% block %} holes; every other template {% extends %} it and fills the blocks. You write the shared chrome once.

templates/base.htmlhtml
{% load static %}
<!DOCTYPE html>

Templates are intentionally limited

You can't call arbitrary Python or pass function arguments in a template — that's by design, to keep logic in views. When you need real computation for display, write a custom template tag or filter in blog/templatetags/, or compute it in the view and pass it through the context.

11 — Free CRUD

The admin site

Django's admin is a full CRUD interface generated from your models — one of the framework's biggest wins. Register a model and you immediately get list, search, filter, and edit screens for staff users. Customise it with a ModelAdmin.

blog/admin.pypython
from django.contrib import admin
from .models import Category, Post, Tag


# The @register decorator ties this config to the Post model
@admin.register(Post)
class PostAdmin(admin.ModelAdmin):
    # Columns in the changelist table
    list_display = ["title", "author", "status", "published_at"]
    list_filter = ["status", "created_at", "category"]      # sidebar filters
    search_fields = ["title", "body"]                        # search box
    date_hierarchy = "published_at"                          # date drill-down bar
    ordering = ["-published_at"]

    # Auto-fill slug from title as you type in the form
    prepopulated_fields = {"slug": ("title",)}

    # Show FK/M2M as a fast typeahead instead of a giant dropdown
    autocomplete_fields = ["author", "category"]

    # Edit these right in the list without opening each row
    list_editable = ["status"]

    # Bulk action available from the changelist dropdown
    actions = ["make_published"]

    @admin.action(description="Mark selected posts as published")
    def make_published(self, request, queryset):
        updated = queryset.update(status=Post.Status.PUBLISHED)
        self.message_user(request, f"{updated} posts published.")

12 — Identity

Auth & the user model

Do this on day one, before your first migrate

Define a custom user model even if it's empty. Swapping the user model after you have migrations and data is one of the most painful changes in Django. Set AUTH_USER_MODEL in settings from the start (shown in §03).

The standard production pattern is a user keyed by email rather than username, built on AbstractUser (keeps Django's permissions/groups machinery) with a custom manager.

accounts/models.pypython
from django.contrib.auth.models import AbstractUser, BaseUserManager
from django.db import models


class UserManager(BaseUserManager):
    # Manager tells Django how to build users without a username field
    use_in_migrations = True

    def _create_user(self, email, password, **extra):
        if not email:
            raise ValueError("Email is required.")
        email = self.normalize_email(email)
        user = self.model(email=email, **extra)
        user.set_password(password)          # hashes — never store raw
        user.save(using=self._db)
        return user

    def create_user(self, email, password=None, **extra):
        extra.setdefault("is_staff", False)
        extra.setdefault("is_superuser", False)
        return self._create_user(email, password, **extra)

    def create_superuser(self, email, password, **extra):
        extra.setdefault("is_staff", True)
        extra.setdefault("is_superuser", True)
        return self._create_user(email, password, **extra)


class User(AbstractUser):
    username = None                          # drop username entirely
    email = models.EmailField(unique=True)

    USERNAME_FIELD = "email"                 # log in with email
    REQUIRED_FIELDS = []                     # prompted by createsuperuser

    objects = UserManager()

    def __str__(self):
        return self.email

13 — Shipping

Static files & deployment

There are two file categories Django keeps deliberately separate. Static files are your CSS/JS/images — code assets you ship. Media files are user uploads. In development the dev server serves both; in production a real web server (or WhiteNoise) serves static, and media lives on disk or object storage.

Nginx serves static/media itself and proxies app requests to Gunicorn → Django

deployment checklistbash
# Surface misconfigurations before deploying (checks DEBUG, SECRET_KEY, HSTS...)
python manage.py check --deploy

# Collect every app's static files into STATIC_ROOT for the web server
python manage.py collectstatic --noinput

# Apply migrations on the server
python manage.py migrate --noinput

# Run under a real WSGI server, not runserver (which is dev-only)
gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 3
Simplest static-in-prod setup

If you don't want to configure Nginx to serve static files, add whitenoise: put its middleware right after SecurityMiddleware and set the storage backend. Django then serves compressed, cache-busted static files itself — perfect for containers and platforms like Railway or Fly.io.
